# Bounded readback at an original depth COPY

`depth::CopyReadback` is a separate, opt-in diagnostic in the regular Vulkan layer. It inserts a depth-aspect image-to-buffer COPY immediately before an admitted original image-to-image depth COPY. The original source layout, usage, contents and original command are preserved. This is a finite CPU export for investigating the missing wide-field regions, not a stereo renderer or an XR transport. The earlier [EndRendering reader](DEPTH_READBACK.md) remains inadmissible in Diablo; its device-wide scope policy has not been relaxed.

## Admission and commands

Set `D4VR_DEPTH_COPY_READBACK_DIAGNOSTIC=1` with a private `D4VR_TRACE_DIR`. Vulkan 1.3, enabled synchronization2 and one physical device are required. A bounded CPU walk inspects at most 256 feature-chain nodes; unrelated enabled features are neither rewritten nor removed. Initialization failure disables this diagnostic and preserves the original device result. Depth audit takes precedence over readback. Camera, replay and XR injection modes must be absent.

Atomically write a regular file `depth-copy.request`:

```text
D4VR_DEPTH_1 1 1707 960 129 1
```

Fields are increasing request ID, exact width/height, format and number of matching original COPY commands (1–4). Formats 129/D24S8 and 126/D32 are admitted. The example dimensions come from the [previous original-transfer observation](ORIGINAL_DEPTH_TRANSFERS.md); dimensions alone do not identify initialized scene depth. Polling occurs at command begin, at most once per 20 ms. One request can be pending; eight copies total are retained without recycling. A regular `depth-copy.stop` containing `1` stops the diagnostic permanently, including pending exports.

The source must be a known optimal, single-sample 2D image with one mip/layer, original TRANSFER_SRC usage and dimensions no larger than 4096 per axis. The original destination must have a known matching format/extent and transfer-destination usage; its creation flags/chains are retained for identity but do not grant source authority. Both original layouts must be GENERAL. The private command accesses only the source and its own buffer. The sole region must cover the full extent at zero offsets, mip/layer zero, with no root/region extension chain. D24's original aspects must include depth and stencil; the added read covers only depth. D32 uses depth. Unknown source-image chains/flags are excluded; the descriptor-layer-alias flag `0x00400000` is admitted without creating a view/descriptor or changing bindings. A concurrent source must include the recording's family. A mutable-format destination with a format-list chain is exercised in the real GPU controls; that does not admit mutable/unknown sources.

Only known primary, unprotected recordings with flags zero or ONE_TIME qualify. SIMULTANEOUS_USE, secondary commands, unknown pool/begin chains and protected pools do not. Both legacy and core/KHR CopyImage entry points preserve the original arguments. The added CopyImageToBuffer2 is downstream, at COPY stage, with a subset of the original source aspects and identical footprint. Its two memory barriers name only its own mapped buffer; no barrier/transition/write touches the application source or destination. There is no intermediate private image.

## Completion and reusable recordings

The diagnostic adds **no queue submission, semaphore wait or GPU host wait** to the current path. If the original QueueSubmit/Submit2 fence is null, the same original call receives a fresh private fence. This explicitly changes the formerly-null fence argument; submit arrays, extension chains, semaphore values/masks and original return remain unchanged. An application-owned fence is preserved and the affected export is disabled. It is never borrowed, reset or destroyed.

Every public submit containing a captured recording invalidates its previous readout **before forwarding** and increases its write epoch. Late successful returns cannot authorize an older epoch. `GetFenceStatus` must confirm the current private fence, and the original call must have succeeded, before CPU readout. A producer mutex serializes that query and bounded copy into immutable CPU words against the next before-submit invalidation. The mutex is released before the original driver call and file I/O; no GPU wait occurs under it. An already exported slot is never read again, even if the recording later rewrites its retained buffer.

A private fence can remain pending behind a later batch waiting for a future application signal. Polling does not wait for it or insert a marker behind that dependency. Eight lifetime fences and eight coherent mapped buffers, at most 128 MiB of reserved memory, bound the diagnostic. Fence/allocation-budget failure disables the affected export without rejecting the application. Unknown submit structures or sparse submission halt the diagnostic, preserving original calls. Single-device masks zero and one are admitted; semaphore scopes are not widened. The exact NV latency-submission annotation is admitted unchanged (and, for legacy submits, may accompany the timeline-value structure). Other chains still halt the diagnostic. This annotation associates application submissions with a frame; it does not define memory scopes and is never used as our pose/scene identity. See the [Khronos contract](https://docs.vulkan.org/refpages/latest/refpages/source/VkLatencySubmissionPresentIdNV.html). The owned GPU calls enable the extension and preserve six annotations per execution; this does not claim that a driver advertising extension revision 2 performs revision-3 explicit attribution.

Reset/free removes the current command lookup, not the resources already named in its recording. Inserted buffers and private fences remain alive until **all actual device work** finishes; teardown may block on device idle. Stop, original failure and device loss never turn unfinished work into a valid receipt. Hidden/downstream submissions, external memory producers and arbitrary extension behavior are outside this diagnostic's established model. This is not a general asynchronous multiqueue engine or a VR-cadence guarantee.

## Exports and evidence

`depth-copy-PID-DEVICE-COPY.bin/.json` retain original request/copy, source/destination generations, recording, original copy ordinal, successful local submission and write epoch, family, format, footprint and aspects. D24 exports mask undefined high padding bits, preserving low 24 depth bits; D32 retains native binary32 words. No linearization, meters, camera pose, present ID or common time is invented. Whole-scene, initialized-pixel, XR-pose and common-time claims stay false.

CPU status reports are bounded to 32 per device and available before destruction, periodically and through `depth-copy-status.request`. Reports obtained during GetDeviceQueue have observed-present boundary zero. Six rejection counters distinguish command, call shape, lookup, source admission, extent/usage, and region failures. One bounded last-depth candidate retains format/extent, source admission/flags/chain presence, destination flags/chain presence, command admission and family, preferring the requested footprint. It is a CPU observation, not a capture or scene identity. Their counters describe host observations, not GPU timestamps. Synchronous allocation, mutex contention, CPU copies and file exports can delay the application.

[depth-copy-readback-v1.json](proofs/depth-copy-readback-v1.json) records the final source/binary fingerprints and owned checks. Twelve native/Steam Runtime executions cover direct production, real-loader enabled/disabled controls and real X11/WSI. Geometry renders different known depths, writes stencil, and independently reads original destination depth, color and stencil. A flags-zero recording is resubmitted on another real queue with changed depth; only the second epoch is exported. One case uses host completion without an interqueue timeline, another uses a COPY-scoped timeline; these controlled application dependencies are not added to the producer. A later future-signal batch keeps the private fence pending while another queue overwrites the original source, and no premature export appears. An application fence bypass is checked. All original byte references remain exact and Khronos synchronization validation reports zero errors.

The WSI reference is deliberately **clear-only D32**, distinct from geometry-depth checks. It submits the same flags-zero recording twice, with original COPY|BLIT signals and device mask zero, before presenting 64 times. The second epoch's private clear is exact and color remains unchanged. Portable controls separately cover late callbacks, CPU read/resubmit exclusion, failure, budgets, stop, reset, unsubmitted work, immutable generations and long/cyclic feature-chain bounds. The test-only CPU gate is not a GPU wait in the producer. It holds the read gate for a bounded 100 ms opportunity for contention; removing the readout mutex in a private negative-control build fails this test in three executions. This is not an exhaustive scheduler proof. Windows compiles the common ownership component; native D3D12/VR integration remains absent.

The completed actual-game result exports one D24 readout at 1707 × 960: 6,554,880 bytes, 1,638,720 pixels, 223,074 distinct defined depth words, including 33,888 zero words. Source flags are `0x00400000`, while the original destination has the additional MUTABLE_FORMAT flag (`0x00400008`). The earlier policy wrongly filtered that destination as though it were the source; the final policy preserves strict source admission. One private fence authorizes epoch 1, with no observed budget/allocation/original-submit failure. The 156 ms host request-to-export log interval is not GPU latency. The user controlled entry/exit; the world looked normal, the launcher returned zero, all owned processes exited and originals plus 262 exports remain identical. No in-game Khronos, exact original-pixel comparison, common-time depth/color pairing, DeviceDestroy trace or final fence counters are claimed.

The actual-game result is recorded separately in [diablo-depth-copy-v1.json](proofs/diablo-depth-copy-v1.json). Neither these owned checks nor an original-view depth export establishes a repair of the wide-field holes. Correlating admitted depth with held reference/wide/return color and identifying initialized regions/passes remains necessary before inferring missing geometry or a downstream cause. No Diablo image has reached the Quest.
