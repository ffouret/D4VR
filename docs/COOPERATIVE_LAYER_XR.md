# Cooperative Capture → OpenXR in the real Vulkan layer

The regular layer now has an opt-in `CooperativeCapture` driver connecting its existing `CaptureProjection` to `ProjectionSession`. Poses originate in `xrLocateViews`; original application render commands produce successive eyes using those camera revisions; actual completed `GpuFrame` leases reach the XR swapchains. There is no application-command replay, external pose file or private CPU image consumer on this path.

**Verification is real X11 WSI and the loader, with owned geometry and a simulated XR runtime. No Diablo-to-XR or physical SteamVR/Quest trial has occurred with this driver.** This is a successive diagnostic source, not a simultaneous scene, low-latency headtracking or continuous immersive Diablo. The later [view/depth calibration trial](VIEW_CALIBRATION.md) uses the separate external-pose driver in the real game and exposes unresolved wide-FOV coverage. Its version-2 source-depth profile is also checked through this cooperative driver with the mock runtime.

## Explicit configuration and ownership

Build the regular layer with `D4VR_TRACE_WITH_COOPERATIVE_XR=ON`. Enable `D4VR_COOPERATIVE_XR_DIAGNOSTIC=1`, mutable camera buffers, validated initial paired packets and a private sequential capture directory. An explicit `D4VR_XR_LOADER` is required. The external-pose diagnostic, dry run, borrowed-binding probe and closed replay modes cannot run concurrently. The regular diagnostic remains available separately.

The first eligible single-swapchain presentation establishes extent, format and borrowed queue. All enabled graphics queues must still be registered in BoundaryUpdates; one graphics family only. The source owns at most one request, two selected leases and four deferred foreign-queue retirement entries. Capture keeps four images / 256 MiB; the presenter keeps its existing one-frame private command/fence and two XR swapchains. There are at most eight requests per controlled device lifetime. No resize/rebinding/restart is inferred.

`camera-pair.bin`, `eye.selection`, `present.request` and `pose.request` do not supply camera/eye input in this mode. Command recording snapshots the desired eye once at BeginCommandBuffer, as in the preceding diagnostic. The request's original identity, time, flags, views, FOV, anchor and clipping planes survive all polling and GPU revision remapping. Receipts keep the actual original capture/present/lease IDs and exact packet observations; sceneSequence remains zero. Unknown/mixed observations cannot become admissible through a newer pose. Strict coherent receipts are unchanged.

Source `record` writes a private `xr-pair-<request>.json` receipt before consumer submission. **A receipt alone does not establish XR submission.** The cancellation test can record images and then discard that XR frame. The runtime readback is checked separately against the corresponding original source frames. Metadata and raw images stay private; only aggregate evidence is published.

## Runtime scope and queue coordination

`advance` runs after the original QueuePresent call, before the wrapper returns, while its caller still owns that queue's Vulkan external synchronization. Construction, each advance and session destruction run with **neither cameraMutex nor stateMutex held**. Source callbacks briefly acquire cameraMutex for the existing bridge. No free worker or extra concurrent borrowed-queue use is introduced.

A persistent, nestable BoundaryUpdates write hold spans each whole runtime scope. Reentrant `before`, `after`, queue registration and `boundary` cannot clear that hold. Existing write memory dependencies are still inserted where required, but no new camera revision is queued during the scope. Entry marks the borrowed queue uncovered; exit queues a marker covering both public reentrant work and private downstream presenter/runtime work. Later camera updates still require coverage and completed marker fences on **all** tracked graphics queues. A nested portable test verifies that a completed reentrant `after` cannot accidentally release inhibition or consume the pending boundary.

Public QueueSubmit/Submit2 (including the KHR alias), BindSparse, QueueWaitIdle and Present participate in the guard. GetDeviceQueue/2 retain registration. Same-thread synchronous runtime reentry can use the borrowed queue. Another thread attempting that reserved queue, a synchronous runtime call using a different queue, or a reentrant WSI presentation is refused before forwarding, with `VK_ERROR_UNKNOWN`, and terminates this diagnostic. The guard does not wait for a runtime worker while that worker waits for its queue. DeviceWaitIdle is also refused from an overlapping non-owner thread. Other application queues remain tracked and may progress under their own external synchronization; the camera write hold persists.

This is deliberately a **restricted cooperative runtime contract**, not a proof for arbitrary asynchronous runtimes. Public calls can be guarded; work secretly submitted through cached downstream dispatch or on another runtime worker outside the scopes cannot be detected or made safe here. Hidden waits on future application submissions can also stall runtime pacing/teardown. Such access/dependency graphs remain unsupported. The simulated runtime exercises synchronous reentry and explicit refusal, not SteamVR's full threading model. No physical SteamVR DRM/WAW issue is resolved by it.

The [Vulkan WSI specification](https://docs.vulkan.org/spec/latest/chapters/VK_KHR_surface/wsi.html) and [swapchain semaphore guide](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html) distinguish acquisition/presentation completion from ordinary submission fences; the test confirms acquisition explicitly.

The render path can block at xrWaitFrame, runtime calls and destruction. Source waiting preserves the old predicted display time; it never claims a newly current pose. Gap 64 bounds presentation counts only, and a missing admissible first eye has no automatic time deadline. `pose.stop` containing `1\n` stops terminally; pending runtime/consumer work drains before leases are released. On device destruction, the caller owns all queues: complete device work, destroy the XR session while the layer/device lookup and producer are alive, retire deferred foreign leases on their actual origins, complete retirement markers, then destroy private resources. The nested XR report is captured before session destruction; coordinator finish/lease counters describe the actual later cleanup.

## Evidence and limits

`tools/cooperative_layer_validate.py` creates real WSI and uses the real layer, GPU producer and presenter. Its simulated runtime reenters GetDeviceQueue, QueueWaitIdle, QueueSubmit and Submit2, including a nonempty Submit2 with owned GPU resources. Teardown checks that this outstanding runtime fence has completed before freeing those resources. Original application draws are counted, and actual XR pixels are compared byte-for-byte to independently saved original rendered frames selected by each receipt's present ID. Two depths distinguish geometric disparity from a uniform screen shift; two runtime poses distinguish view changes from static images.

Controls cover ordinary delivery, XR image-wait timeouts, a runtime stop during source waiting, file stop, early device teardown, foreign producer retirement on its origin queue, and rejected worker/foreign-runtime-queue access. They run natively and inside Steam Runtime with Khronos synchronization validation. Application shared resources in the foreign-queue fixture are explicitly chained with a timeline signaled **on the actual producer queue**, and WSI acquisition is host-fence-confirmed and each image is presented on its producer queue; that queue differs from the established XR consumer during the foreign interval. Earlier attempts exposed a missing cross-queue memory dependency and presentation hazards in the fixture. Separate production/presentation queues remain unvalidated here. These fixture waits are not added to the layer's normal path; this is not an unmodified asynchronous game renderer test.

The original tagged WSI vertex shader retains its own projection and applies the requested view transform. Its later opt-in version-2 branch applies optical X/Y and scaled source depth, as described in [VIEW_CALIBRATION.md](VIEW_CALIBRATION.md); the real game's wider coverage still fails. Before a game/HMD projection trial, finish anchor/orientation and scene-coverage calibration, then audit the physical runtime's dispatch/threading/dependency behavior against the restricted queue contract, with an explicit time limit and stop path. Common component compilation on Windows does not provide native D3D12/VR integration.

Aggregate evidence: `docs/proofs/cooperative-layer-xr-v1.json`.
