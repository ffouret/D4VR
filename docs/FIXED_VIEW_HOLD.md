# Fixed monoscopic view between diagnostic captures

The earlier fragment experiment's five-second gap **did not hold the transformed camera**: `CaptureProjection::wantedEye()` returns the original-pipeline selector after completing a pair. Its raw images and packet receipts remain valid, but the claimed five-second temporal settling is withdrawn in [FRAGMENT_PROJECTION.md](FRAGMENT_PROJECTION.md) and its aggregate proof. This step adds an explicit held-view mode and observes the submitted packets between requests.

## Contract and evidence scope

`D4VR_DIAGNOSTIC_VIEW_HOLD=1` is opt-in and requires the external pose diagnostic, mutable GPU packets and its exclusive mode. It is separate from cooperative XR and remains disabled by default. `DiagnosticCapture` additionally accepts `holdMonoscopicView=true`. A request must have identical left/right view mappings, projections, flags, depth scale and gates. Stereo requests are refused before entering the mailbox. At most eight requests are accepted in this mode.

Once the actual mailbox revision is acknowledged against `BoundaryUpdates`, the driver retains selector 0 whenever the source would otherwise choose the original pipelines. During a pair it still selects the original two distinct GPU images and original eye identities; identical monoscopic mappings make that temporary eye switch geometrically equivalent. The held state retains a packet observation, **not image leases**. No idle image copy is requested between completed capture requests; the recording-thread gate uses an atomic value. Packet updates, queue synchronization, producer/consumer fences and foreign-queue retirement keep their existing contracts. Terminal stop clears the hold and returns newly recorded commands to original pipelines. Already recorded commands are not rewritten, and already submitted consumer work retains its resources until completion.

`FixedViewHold` observes only intervals with successful selected-draw submissions, mask 0-only, a uniform exact packet and consecutive presentation IDs. An unknown/mixed packet, missing present or reversed host clock breaks the current run. It retains the longest contiguous run, original packet/submit IDs, and monotonic **host** start/end times. A by-value receipt is frozen when the next request is accepted and records whether that original mapping matches the new request. A later revision cannot repair or retag the old observation.

This proves continuity of the **selected-draw packet observations**, with a host presentation span. It does not measure GPU elapsed time, establish all-pass camera coverage, identify a correct temporal history, certify current XR time or invent a common scene instant. The normal source receipts remain successive and partial. An application can still block in its existing rendering/presentation calls; no VR cadence is established.

## Verification

Portable CPU controls cover default/held selection, monoscopic rejection, original receipt immutability, exact packet mismatch, unknown observations, missing present IDs, reversed host time and a five-second controlled host interval. The common test runs on Windows and Linux, including ASan/UBSan.

Eight real X11/WSI/loader cases use the fragment packet-equality shader and mutable camera packets. Ten pairs compare 5,242,880 bytes exactly with the application's original readback. Independently saved idle frames 16, 30 and 35 equal the captured translated view, which differs from the original camera. Source eye/revision/translation agree in both shader stages. A valid stereo request is not admitted; short runs, a foreign producer queue, cancellation, terminal stop and original-image restoration are covered. Four default-driver regression cases additionally preserve their prior behavior. Two negative controls disable the driver hold while keeping the same monoscopic fixture and detect the absent held interval. Khronos synchronization validation loads and reports zero errors. These are owned scenes with explicit fixture synchronization, not a generic asynchronous engine or SteamVR compatibility proof.

The new actual Diablo experiment and exact measured spans are recorded in [fixed-view-hold-v1.json](proofs/fixed-view-hold-v1.json). It reuses the unchanged partial shader bundle from the fragment experiment, with six requests for baseline/wide/return and intervening held intervals. No shader bundle is silently expanded and no game/vendor original is replaced. Raw game pixels, shader identifiers and logs remain private.

The actual Diablo session completed with the unchanged partial shader bundle and a newly validated layer. Its three measured mappings follow **871, 874 and 873 consecutive uniform selected-draw intervals**, spanning **6,029, 6,047 and 6,044 host milliseconds**. Each frozen preceding receipt matches the previous capture's exact GPU packet and the next request's mapping. The packet revision remains its original revision; the measurement capture receives a separate revision.

At the wide 91.67° field, large missing regions remain visible. Twenty-five of 42 contrasted terrain patches follow the optical mapping with zero residual and return to their initial coordinates. This still does not prove correct history in all passes or isolate culling from later color processing. Normal UI exit completed, launcher returned zero, all owned processes exited and the originals/262 exports match before and after. No new in-game Khronos, D32 or final device/fence accounting is claimed. No relaunch is needed for those absent final counters.

The next useful discriminator is a bounded attachment-depth readback at an original valid rendering boundary, compared with the final color image. It was absent from the held-view milestone; the subsequent [depth-readback implementation](DEPTH_READBACK.md) now passes owned GPU/WSI controls but has not been run in Diablo. Existing private metadata shows transfer-source usage and GENERAL layout on the old observed depth attachment; that is preparation, not a captured game-depth result. The [Khronos copy rules](https://docs.vulkan.org/spec/latest/chapters/copies.html) require separate depth/stencil aspects, proper transfer synchronization and supported source usage. An added read cannot be assumed covered by the application's original synchronization.

Wide-FOV coverage, upstream visibility/culling versus downstream effects, all-pass temporal correctness, the diorama anchor/gravity, physical SteamVR DRM/WAW issues, simultaneous stereo, continuous cadence and native Windows D3D12/VR remain unresolved. No Diablo image has reached the Quest.
