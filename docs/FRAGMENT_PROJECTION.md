# Fragment projection dependencies and explicit fixed-view diagnostic

Some observed Diablo fragment shaders read the source camera projection again after interpolation. Editing only a vertex's projection leaves this second calculation unchanged. This step follows those concrete consumers, adds an explicit fragment constructor, and binds the same GPU camera packet to both admitted stages. It does not establish correct temporal history or complete wide-FOV coverage.

## Original consumer evidence

Two previously recorded real frame traces supply **20 actually used pipeline records** for the six partner-reading vertex candidates. The driver-specific module-identifier catalogue yields unique fragment candidates for 18 records, covering nine distinct fragment candidates; two records share an unresolved fragment identity. These are pipeline-stage associations under that pinned driver/catalogue, not a match inferred from location numbers and not a cryptographic identity or full-frame coverage claim.

`tools/fragment_slice.py` validates immutable original fragment snapshots with SPIR-V validation, then walks a closed backwards slice of a selected output's values under the pinned Khronos grammars. Four original candidates resolve pure arithmetic routes from inputs at locations 1 and 4, camera projection rows 72/73/75 and camera row 52 into output location 0. The calculations divide projected coordinates, combine them with the interpolated partner coordinates and row-52 components, and pack the result numerically. Five other candidates are refused when the selected value route reaches an unmodeled texture sample. Those refusals are not silently treated as arithmetic.

The model conservatively combines components and phi/select alternatives. It does **not** trace branch effects, other output values, resource consumers of the resulting render target, executed branches, coefficient sensitivity or temporal meaning. Its reports cannot identify current/previous-frame semantics or the cause of missing geometry. Row 52, source models, inverse matrices and ClipDistance remain unchanged. Unit graph fixtures are separate from valid compiled-SPIR-V controls; a separate normalized logical-address control exercises slicing, while physical-address shaders drive the GPU references.

## Fragment construction and native binding

`spirv_probe --stereo --helper-no-telemetry --projection-only-helper --projection-input --fragment-projection-input` explicitly admits one Fragment entry and one original function with the existing canonical, static projection-load contract. Four helper calls transform the source projection columns, producing four Function-local rows before the original body. Existing row/component loads read those rows. Original stores are retained; no additional original output, Uniform or external store is introduced. No VertexIndex is invented: the helper must pass the projection-only write contract **and** leave its vertex-identity argument unused. Valid helpers that use that argument are refused.

The output carries `D4VR_FRAGMENT_PROJECTION_INPUT_1` plus the existing stereo ABI marker and specialization ID 4. `eye::Control`, owned graphics-library stages and `Recipe` specialize only explicitly marked fragments. A fragment never grants vertex authority: an executable with no admitted vertex is still refused. Ignored library subsets stay ignored, and unrelated specialization constants remain owned and unchanged. Packet-update barriers now include both vertex and fragment readers; queue-family ownership, bounded markers, reader completion and runtime write inhibition retain their existing requirements.

The fragment mode is projection-only. The separately labeled vertex partner mode changes both original projection windows with **one fixed transform**, retaining their separate source coefficients. Neither mode has a previous XR pose, history invalidation or jitter-history policy. A dynamic HMD feed is not authorized by these controls.

## Owned GPU and real loader checks

The independent owned reference transforms source geometry on the CPU, supplying matching optical projections to its uninstrumented vertex and fragment calculations. Native and Steam Runtime executions each compare 48 cases: **12,582,912 RGBA bytes with zero differences** and **605,086 D32 texels**, maximum error 0.000000178814. The allowed color-edge bound remains 64 bytes per case; observed differences are zero. Keeping the fragment on its original projection makes this same color reference fail, with zero validation errors. Wrong-inverse and copied-partner controls remain distinguishable. The owned fragment deliberately tests a projected-coordinate visibility dependency; this is not an assertion that Diablo's resolved fragment output controls visibility.

A separately rebuilt full optional-XR layer passes eight **real X11/WSI/loader** cases with mutable packets, external diagnostic poses and actual Capture leases. A vertex forwards its packet eye, revision and translation; the fragment independently reads its own specialized packet and paints a mismatch magenta. Ten captured pairs compare **5,242,880 original pixel bytes exactly**, have no mismatch pixels, and retain depth-dependent disparity and pose changes. A foreign producer queue, short run, terminal cancellation and teardown are covered. Both environments' negative controls omit the fragment marker and detect the mismatch. Khronos synchronization validation loads and reports zero errors throughout. This is an owned scene with explicit fixture synchronization, not a proof of an arbitrary game's asynchronous queues or physical SteamVR.

The native CPU tests cover marked/unmarked stage admission, specialization ownership, graphics-library subsets/links, fragment-only refusal and packet barriers. CI compiles the full layer, runs construction/slice controls without a GPU, and tests common components on Windows plus Linux ASan/UBSan. Windows D3D12/VR integration remains absent.

## Real-game experiment and remaining work

A separate private admission preserves the already validated 5,373 primary-vertex overrides and overlays only three hash-verified partner vertices plus four associated arithmetic-slice fragments. The five multi-function vertices previously excluded remain original; unresolved/other fragment stages are not rewritten. This narrow scope is explicitly **partial and fixed-monoscopic**. Source hashes, helper/GPU proof, WSI layer proof and original-store preservation are checked before preparation; old certificates and baseline artifacts are not rewritten.

The new real Diablo session completed without OpenXR or a headset: six successive pairs at 2560×1440 cover baseline, wide field and restored baseline, each with paired requests separated by five seconds. Both view transforms are identical and monoscopic; the two exports still have distinct presentation IDs. Three of the four fragment override loads and all three vertex override loads are observed in the game log; a load does not prove a particular branch executed. The fourth fragment's load is not observed.

Twenty-one of 46 contrasted terrain patches pass the optical-mapping and return checks. All 21 favor the expected optical mapping over the unchanged-image hypothesis, 20 have zero optical residual, and all 21 return to their original coordinates. **Large missing/discontinuous regions remain at 91.67°**. This is a coverage failure, not a complete view or a measured improvement over an earlier lighting/session. The last sampled pipeline graph has zero driver/budget failures; no in-game Khronos or final fence-accounting claim is made. Terminal stop was written, normal UI exit completed, launcher returned zero, all owned processes exited and the original files/262 named exports match before and after. Do not relaunch just for missing final teardown counters.

The game experiment and its result are recorded separately in [fragment-projection-v1.json](proofs/fragment-projection-v1.json). Raw game shaders, identifiers, blocks, images and logs remain private. Neither construction nor an original-pixel comparison in the owned scene proves that all game passes share a camera. Physical SteamVR's earlier DRM/WAW errors, the diorama anchor/orientation, coherent simultaneous eyes, continuous VR cadence and native Windows integration remain open. No Diablo image has reached the Quest.

This narrow result does not rule out every partner or temporal dependency. Repeating the same fixed-view capture or disabling original clip distances would not establish the missing cause.
